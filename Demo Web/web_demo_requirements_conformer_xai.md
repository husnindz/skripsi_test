# Medical Check-up Conformer XAI --- Web Demo Requirements

## 1. Project Goal

Build a lightweight web demo for the existing **Tabular Conformer
medical check-up prototype**.

The demo is for **prediction and Explainable AI (XAI) visualization
only**. It is not a medical diagnosis system.

The application must be simple enough to deploy to **Hugging Face
Spaces** later.

## 2. Important Architecture Requirement

Use a **MONOREPO** so frontend, backend, model artifacts, and deployment
configuration are kept in one repository.

Recommended structure:

``` text
medical-conformer-demo/
│
├── frontend/
│   ├── src/
│   ├── public/
│   ├── package.json
│   └── ...
│
├── backend/
│   ├── app/
│   │   ├── main.py
│   │   ├── schemas.py
│   │   ├── model.py
│   │   ├── preprocessing.py
│   │   └── explainer.py
│   ├── requirements.txt
│   └── ...
│
├── models/
│   ├── conformer_model.pth
│   ├── scaler.pkl
│   └── config.json
│
├── Dockerfile
├── README.md
└── ...
```

The exact framework may follow the existing project convention, but keep
frontend and backend separated inside the same repository.

## 3. Authentication

**DO NOT implement login, registration, authentication, user accounts,
sessions, or database-backed users.**

The demo must be accessible directly.

Opening the application should immediately show the prediction
interface.

## 4. Main User Flow

The entire application should have a simple flow:

``` text
Open Web
   ↓
Medical Check-up Input Form
   ↓
Submit / Predict
   ↓
Backend preprocessing
   ↓
Conformer inference
   ↓
4-class probabilities
   ↓
Predicted class
   ↓
SHAP XAI explanation
   ↓
Display prediction + feature contributions
```

No dashboard, admin panel, user management, or complex navigation is
required.

## 5. Input Features

The input form must follow the exact feature order used by the trained
Conformer:

``` text
JENIS_KELAMIN
UMUR_TAHUN
cholesterol total
creatinin
fbs
rbs
hgb
lymfosit%
mch
mchc
mcv
ureum
wbc
```

Do not rename or reorder these fields arbitrarily in the backend.

The backend must maintain one canonical `FEATURE_ORDER` configuration so
training and inference use exactly the same order.

## 6. Input Form

Create a clean medical check-up form containing all 13 features.

Suggested input types:

-   `JENIS_KELAMIN` → select/input matching the training dataset
    representation
-   `UMUR_TAHUN` → numeric input
-   laboratory values → numeric inputs

Each numeric field should have:

-   clear label
-   appropriate numeric input
-   validation for invalid/non-numeric values
-   optional helper text where useful

Do not invent clinical reference ranges unless they are explicitly
provided by the project data.

The UI should not imply that a value is medically normal/abnormal unless
that information is actually provided by the model/data.

## 7. Prediction Classes

Use the exact existing target mapping:

``` text
0 → Sehat / Tidak Ada Indikasi
1 → Jantung dan Pembuluh Darah
2 → Spes. Penyakit Dalam
3 → Spes. Paru-Paru
```

The frontend must display the class name returned by the backend.

Do not hard-code a different mapping in the frontend.

## 8. Prediction Result

After submission, display:

### Predicted Class

Example structure:

``` text
Predicted Result

Spes. Penyakit Dalam
```

### Probability

Display probabilities for all four classes:

``` text
Sehat / Tidak Ada Indikasi       XX%
Jantung dan Pembuluh Darah       XX%
Spes. Penyakit Dalam             XX%
Spes. Paru-Paru                  XX%
```

A simple horizontal probability bar or clean chart is sufficient.

Do not use the probability as a statement of medical certainty.

## 9. XAI / SHAP Result

The demo must show the SHAP explanation for the prediction.

The primary local explanation should answer:

> Which input features contributed most to this model prediction?

Display the most important features, for example:

``` text
Feature              Value       SHAP Contribution
---------------------------------------------------
fbs                  ...              +0.XX
ureum                ...              +0.XX
wbc                  ...              -0.XX
...
```

Use the actual SHAP values generated by the backend.

Interpretation:

-   positive SHAP → pushes the model output toward the explained class
-   negative SHAP → pushes the model output away from the explained
    class
-   larger absolute SHAP → stronger contribution to that model output

Do not describe SHAP as causal medical evidence.

## 10. SHAP Visualization

The primary visualization should be a horizontal contribution chart.

Conceptually:

``` text
Feature A       ███████████  +0.42
Feature B       ███████      +0.28
Feature C       ███          -0.13
Feature D       ██           -0.08
```

Show approximately the top 5--10 features by absolute SHAP value.

Keep the visualization readable on desktop and mobile.

## 11. Backend

Recommended backend responsibilities:

``` text
POST /predict
       ↓
Validate input
       ↓
Apply saved preprocessing
       ↓
Convert input to model tensor
       ↓
Load Conformer
       ↓
Generate logits
       ↓
Softmax probabilities
       ↓
Generate SHAP explanation
       ↓
Return structured JSON
```

The backend should be the single source of truth for:

-   preprocessing
-   feature order
-   target mapping
-   model inference
-   probability calculation
-   SHAP calculation

The frontend must not reimplement model logic.

## 12. API Response

Use a response structure similar to:

``` json
{
  "prediction": {
    "class_id": 2,
    "class_name": "Spes. Penyakit Dalam"
  },
  "probabilities": {
    "Sehat / Tidak Ada Indikasi": 0.08,
    "Jantung dan Pembuluh Darah": 0.10,
    "Spes. Penyakit Dalam": 0.76,
    "Spes. Paru-Paru": 0.06
  },
  "explanation": {
    "features": [
      {
        "feature": "fbs",
        "value": 180,
        "shap": 0.42
      },
      {
        "feature": "ureum",
        "value": 50,
        "shap": 0.21
      }
    ]
  }
}
```

The exact numerical values above are only an example of the response
format. The application must return real model/SHAP output.

## 13. Model Artifacts

The deployment must load the same trained model and preprocessing used
during the Conformer experiment.

At minimum preserve:

``` text
Conformer weights
Scaler
Feature order
Target mapping
Model configuration
```

Recommended:

``` text
models/
├── conformer_model.pth
├── scaler.pkl
└── config.json
```

`config.json` should contain model configuration such as:

``` json
{
  "d_model": 64,
  "num_heads": 4,
  "num_layers": 2,
  "ffn_dim": 128,
  "conv_kernel_size": 3,
  "dropout": 0.1,
  "num_classes": 4
}
```

Do not manually duplicate architecture settings in multiple places.

## 14. SHAP Performance

SHAP can be computationally expensive.

For the web demo, prioritize **local explanation for one submitted
patient**.

Do not calculate a full global SHAP analysis for every request.

The notebook may be used for global analysis, while the web backend
focuses on local explanation.

If the selected SHAP algorithm is too slow for interactive inference,
use a lightweight/appropriate SHAP configuration while keeping the
explanation method consistent with the trained model.

## 16. Loading and Error State

The UI must provide:

-   loading state while prediction is running
-   validation error for invalid inputs
-   backend error message if inference fails
-   clear reset button
-   disabled predict button while request is processing

Do not expose Python stack traces to the end user.

## 17. Medical Disclaimer

Include a concise disclaimer near the result:

> This demo is an experimental machine-learning prototype. Its
> prediction and explanations are based on the trained model and should
> not be interpreted as a medical diagnosis or a substitute for
> professional medical evaluation.

Do not make stronger medical claims than the model actually supports.

## 18. No Database

A database is **not required**.

Do not add:

-   PostgreSQL
-   MongoDB
-   user accounts
-   prediction history
-   patient storage

The demo should process the submitted input and return the result
without permanently storing patient data.

## 19. Hugging Face Deployment

The application should be prepared for deployment to **Hugging Face
Spaces**.

Prioritize:

-   Docker-compatible deployment
-   environment-variable based configuration where needed
-   no dependency on local development paths
-   model artifacts accessible inside the deployed repository/container
-   single command/container startup
-   frontend and backend working together inside the monorepo

The deployment must not depend on `/mnt/data/...` paths.

## 20. Monorepo Deployment

The repository must remain a monorepo:

``` text
medical-conformer-demo/
├── frontend/
├── backend/
├── models/
├── Dockerfile
├── README.md
└── ...
```

The deployment configuration should allow the complete application to be
built and started from the repository root.

## 21. Out of Scope

Do not implement:

-   login
-   registration
-   authentication
-   database
-   patient history
-   admin dashboard
-   appointment system
-   payment
-   Llama integration
-   chatbot
-   medical diagnosis logic
-   manual clinical rules
-   fabricated medical reference ranges

The current scope is only:

``` text
Input
  ↓
Conformer prediction
  ↓
4-class probabilities
  ↓
SHAP local explanation
  ↓
Display result
```
